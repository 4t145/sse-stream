本轮于 2026-09-11 对当前工作区做了逐项优化实验。基线仍包含原有未提交改动，源码 SHA-256 为 `cf624a4177455f6831e86f095391b3df908268e5100312931018517f475b43f6`。所有候选实现都在临时工程里验证，未替换工作区的解析实现。

最关键的拖累点要按负载区分：原有小消息场景的主要问题是每个事件经过过长的处理流程；长非 ASCII 数据的主要问题是 UTF-8 校验；极碎输入的上限受输入对象和每块处理成本约束；大小混合事件还有历史容量持续膨胀的问题。长中文数据的校验瓶颈是本轮新发现的最大收益点，原有 13 个全 ASCII benchmark 无法揭示它。

**怎样区分因果和组合收益**

本轮编译了 17 个实现（当前基线、16 个候选），加上 sse-core 对照。第一轮对 17 个负载测 12 个实现加 core；第二轮用借用切片和 ready stream 检查代表负载；随后对新增候选组合复测。筛选每组交错运行 31 轮，每轮打乱实现顺序，每个测量块目标 5 ms，并与同轮基线配对。该方式用于观察单项变化的方向，减少前后相隔较久造成的温度、频率与负载差异。

最终组合另外通过原 Criterion bench 三轮验证，每轮轮换 core、基线、原型的运行顺序；每项 40 个样本，预热 0.15 s，测量目标 0.8 s。机器为 i5-13600K，固定逻辑 CPU 2，Rust 1.98.0。未锁定频率、未采集硬件性能计数器，仍存在宿主机噪声，不能把所有小幅差异都视为稳定收益。

原始实现、候选、输入类型和 benchmark 构建上下文必须区分：交错筛选用于定位拖累点，最终 Criterion 用于复核端到端表现；不能直接拼接两种 harness 的绝对耗时。

**1. 对小消息，最先应该缩短事件完成时的流程**

把快捷路径拆成了两种，避免将流程和分配的变化混在一起：

| 单项实验 | 小消息整流块耗时变化 | 小消息 TCP 块耗时变化 | 实际改动 |
| --- | ---: | ---: | --- |
| 提前分发 | -17.2% | -17.4% | 保留 push_data_line、换行 push/pop、dispatch 和原分配策略，仅识别紧接的空行并直接完成事件 |
| 直接构造 String | -21.7% | -21.6% | 完整单 data 行直接验证、复制到输出 String，跳过累积与通用分发 |
| 显式 reserve 分隔符空间 | -7.2% | -7.5% | 提前预留 data 长度加 1，避免随后 push 导致首次扩容 |
| 保留 staging、每次复制输出 | -6.1% | -6.0% | 真正复用 staging Vec，但额外复制 payload |

这里的百分比是交错筛选中配对耗时比的中位数，不是可相加的分项占比。尤其 reserve 的收益在 borrowed/ready 模式里接近零，不应全部归因为分配器。

“仅提前分发”仍保留原分配策略，却取得了大部分小消息收益，给出了最直接的证据：完整事件不需要再进入一次通用行扫描与事件边界流程。相比之下，10 万小事件的分配计数，当前为约 100002 次 alloc，直接构造版本为 100000 次；不存在稳态从两次 malloc 变一次 malloc 的变化。

优先补丁：[event-boundary-only.patch](bench-study-2026-09-11/event-boundary-only.patch)。它相对当前源码独立应用，保留原 UTF-8、累积和分配逻辑。完整单行直接构造的更多收益也有验证，但应作为下一步独立审阅，不能把它称作零复制：仍需生成拥有所有权的 String。

**2. 对长中文或混合文本，UTF-8 校验是最重的拖累**

单独将较长字段的标准库校验换成 `simdutf8::basic::from_utf8`，在失败时再调用标准库以保持原来的 Utf8Error 位置与错误语义：

| 负载 | 仅替换 UTF-8 校验，耗时变化 |
| --- | ---: |
| 40 KB 级 ASCII，每条一个块 | -16.2% |
| 40 KB 级 ASCII，TCP 分片 | -17.2% |
| 约 40 KB 中文，TCP 分片 | -79.3% |

对照库在这组合法中文负载上也接近当前实现。组合原型三轮 Criterion 中约 0.215 ms，对照库约 1.059 ms，处理的都是同一批 64 条消息；按三轮耗时比的中位数，原型约为 core 的 20.3%，相当于约 4.9 倍吞吐。

又用独立微基准只测合法输入的校验、保持错误返回类型一致，观察到约 40 KB ASCII 的 SIMD/标准库耗时比为 0.376，约 40 KB 中文为 0.126，混合文本为 0.128。微基准与整个解析流程不是同一测量，不能直接相减估算精确函数占比，但与端到端单项实验相互印证。

短输入需要区别处理：8～32 B ASCII 的 SIMD 校验反而慢约 10%～13%，64 B 附近接近持平。本轮原型取保守阈值 256 B；64～128 B 的混合文字已有潜在收益，但尚未针对该阈值完成端到端验证。下一步应在不同架构上选择阈值。

优先补丁：[utf8-only.patch](bench-study-2026-09-11/utf8-only.patch)。实验使用已缓存的 simdutf8 0.1.5，并在错误时回退标准库，不跳过校验、不改为 lossy 解码。这个补丁将它添加为普通依赖；可选 feature 和默认是否开启仍是落地时需要确定的 API/依赖策略。本次 no-default-features 测试关闭的是原有 memchr feature，并不关闭新加入的 SIMD 校验。

**3. 对 4 B/10 B 碎片，重点是每块处理成本，收益有输入类型边界**

仅统一 SseByteStream 的新旧块处理槽位，Bytes + Tokio 输入的小消息 4 B、keepalive 4 B、中等消息 10 B 场景分别减少约 7.0%、8.5%、3.6%。这没有减少输入块数或改变 SSE 输出。

然而在借用切片 + futures ready 输入的诊断模式中，同项变更分别约慢 2.4%、8.2%、4.4%。两种模式同时改变了输入类型和 Pending 行为，不能把差值全归因于原子引用计数；它说明该优化依赖适配层和编译后的路径，不能宣称所有 generic Buf 输入都更快。

上一轮独立的空消费诊断已显示：Bytes clone/drop 是这些人工极碎输入的大项固定成本。两库都承担它，它不能单独解释库间差距，也不能通过只修改 benchmark 来“解决”。原型仍有 4 B 小消息落后 core 的情况，最终三轮比值中位数约 1.073。

补丁：[poll-only.patch](bench-study-2026-09-11/poll-only.patch)。需要注意，这种槽位处理会将耗尽输入块的清理延到后续 poll，可能延长最后一个输入块的持有时间。这是具体的生命周期取舍，应与性能一起评估。仍不建议等待网络数据来凑大块，或者重新引入批量事件队列来换吞吐。

**4. 对大小混合消息，应该管理输出容量，不能全局收缩或复制**

这一轮强制使用 TCP 分片，并让大小消息都包含两行 data，使完整单行快捷路径无法掩盖容量策略的效果。

输入是一条 40000 B data 加 tail，随后 1000 条 `data: x\ndata: y\n\n`。当前实现和 core 都让后面的小消息继承了约 46 KB 的容量。新策略只在 capacity >4096 且实际长度小于 capacity/4 时，将小 payload 复制到紧凑的输出，保留大 staging 供后续累积使用；大小接近时仍转移原缓冲区。

| 指标，1001 条输出 | 当前实现 | 仅条件复制 / 组合原型 |
| --- | ---: | ---: |
| alloc 次数 | 1003 | 1003 |
| realloc 次数 | 5 | 5 |
| 分配与扩容申请字节累计 | 46762420 | 141420 |
| 输出 data capacity 累计 | 46670624 | 49624 |
| 最后一个 3 B data 的 capacity | 46624 | 3 |

这些是分配申请和容量，不是测得的同时驻留 RSS；诊断消费者会立即丢弃输出。这个改动显著减少容量浪费，同时没有增加 realloc。单因素候选在大小混合多行场景耗时减少约 14.5%，完整等长大消息接近不变。

反面实验也很明确：取消下一事件的预留、每次从空 Vec 增长，会让大消息 TCP 分片慢约 21%，普通多行场景慢约 48%；将预留上限固定为 4 KB，会让大消息 TCP 分片慢约 33%；始终保留 staging 并复制输出，会让完整大消息慢约 44%。因此不能只看到内存变少就采用全局策略。

补丁：[adaptive-capacity-only.patch](bench-study-2026-09-11/adaptive-capacity-only.patch)。阈值是当前实验取值，应继续用大小交替、长连接和下游持有事件的负载评估。

**5. 扫描和注释路径仍要分开调，但不是唯一主因**

“短切片标量，长切片直接 memchr2”的单项筛选，在小消息 TCP 场景约减少 13.1%，大 ASCII TCP 消息约减少 6.2%。如果仅在通用扫描函数中额外检查冒号，收益会被每行新增的判断抵消。

将无 debug tracing 的注释识别移到通用 data/metadata 分支之前，并使用原来的短行扫描方法，单独筛选的整块和 TCP keepalive 约减少 8.7%/8.8%。但把所有优化组合后，原 Criterion 三轮并未完全保持这个优势。这修正了筛选阶段“已经解决 keepalive 退化”的初步判断：注释方向有效，最终代码布局和组合仍需进一步控制。

补丁：[early-comment-only.patch](bench-study-2026-09-11/early-comment-only.patch)。本轮未把结果波动简单归因为分支预测或指令缓存，因为没有硬件采样证据；也没有为追求某次更好的数字重复选择性重跑。

**建议优先级与验证范围**

1. 先处理完整事件结束时的重复流程。这直接针对当前常见小消息负载，且有保留原分配方式的单因素证据。
2. 对大 payload 或较多非 ASCII 文本启用经过阈值控制的 SIMD UTF-8 校验。这是本轮最大的绝对收益点。保留标准库错误回退，分别确认默认依赖与可选 feature 的成本。
3. 独立加入按容量比例选择输出方式的策略，解决两库共同的混合负载问题。
4. 将 poll 和扫描优化分开继续验证，重点保留 keepalive、普通多行、借用切片输入的表现，不把组合收益直接归到某个热点函数。

16 个候选都通过了与基线的分片等价性对照；最终组合在 default、all-features、no-default-features 下通过现有 33 个字节解析测试、1 个编码测试及扩展等价性测试。额外覆盖了有效长中文/混合文本、8 KB 数据中多个 SIMD 块边界附近的非法 UTF-8、1～1460 B 多种分片，以及原有 BOM、CRLF、metadata、错误恢复输入。未运行网络集成测试、Miri、长期 fuzz 或 ARM 性能测试。

本轮工作区只增加研究材料，现有源码、测试和 bench 未替换。各单项 patch 都相对本轮基线生成，不能直接假定相互可叠加。[combined.patch](bench-study-2026-09-11/combined.patch) 是完整组合，用于审阅已验证的实现与已知退化。
