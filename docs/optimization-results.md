本轮按两步把通用性能优化落到了源码，并扩充了 benchmark。单行 JSON 是 SSE 的一种数据负载，没有增加 JSON 解析、MCP 适配或专用输出 API。

**实际改动**

第一步包含两项：默认开启、可关闭的 `simdutf8` feature，对至少 256 B 的字段使用 SIMD UTF-8 校验；短字段或 SIMD 校验失败时使用标准库，保留 `Utf8Error` 的类型及位置。同时，编码前一次计算完整输出长度，包含各字段前缀、换行与 retry 字符串，预留最终 Vec 容量。现有公开类型和调用方式不变。

第二步调整 data 输出的容量策略：仅在累积容量大于 4096 B、实际 payload 小于容量的四分之一时，复制出紧凑的输出并保留累积缓冲区。其他情况仍转移原缓冲区，不增加一次大 payload 复制。这解决了大记录后的小记录持续继承大容量的问题，但没有回收连接中保留的大累积缓冲区。

新增的逐字节分片测试还发现并复现了原有缺陷：一个被拆开的 `data:` 前缀恰好在块末尾完成时，解析器会过早清除“跳过下一个可选空格”的标记，导致输出多一个空格，UTF-8 错误位置也偏移。已修复，测试覆盖空块、一个或两个空格、空 data、Body 和直接字节流。

独立补丁按顺序保存在 [分片修复](bench-rollout-2026-09-11/00-prefix-space.patch)、[第一步](bench-rollout-2026-09-11/01-utf8-and-encoding.patch)、[第二步](bench-rollout-2026-09-11/02-adaptive-capacity.patch)。这些补丁用于展示本轮相对原工作区的变化；工作区已经包含这些改动，无需再次应用。

**测量范围与基线**

保留原来的 13 个解析负载，新增单行 JSON、metadata 在 data 后、CRLF、长中文/混合 Unicode、JSON 中的原生 Unicode 与 ASCII 转义、Base64 文本、大后小和大小交替等负载，共 28 个解析场景。另有 5 个编码场景。负载生成统一在 `benches/scenarios/mod.rs`，由仓库 bench 与本轮独立比较工程共享。

性能基线是本轮开始时的工作区加上仅分片空格修复；未修正的原始实现也记录在 `step2.csv` 的 original 行。这样避免将行为修复算作性能优化。第一步完成后独立测量；第二步完成后，把基线、第一步、第二步与 sse-core 放在同一可执行文件中比较。

机器为 Intel Core i5-13600K，固定逻辑 CPU 2，Rust 1.98.0。主要测量交错进行 31 轮，轮内打乱实现顺序，每个块预热后目标约 3 ms，按同轮基线计算比值。CPU 没有锁频。p10/p90 是配对比值的分位数，不是置信区间。

以下采用第二步交错测量的配对耗时比中位数，负数表示耗时下降。表中 TCP 是固定 1460 B 分块的名称，不是抓取的 TCP 包。

| 解析场景 | 最终实现相对基线 | 第二步相对第一步 |
| --- | ---: | ---: |
| 大 ASCII，每条一个块 | -16.3% | +0.1% |
| 大 ASCII，1460 B 分块 | -13.4% | +0.5% |
| 长混合 UTF-8，1460 B 分块 | -74.9% | -0.3% |
| 长混合 UTF-8，每条一个块 | -80.2% | 接近 0 |
| 长中文 JSON，1460 B 分块 | -77.5% | 接近 0 |
| 长 JSON 的 Unicode 转义 / Base64 文本 | -12.6% / -11.1% | +0.4% / +0.3% |
| 大后小 JSON，1460 B 分块 / 整块 | -14.4% / -24.3% | -14.9% / -26.0% |
| 大后小多行，1460 B 分块 / 整块 | -15.6% / -25.3% | -15.5% / -25.4% |
| 大小交替，1460 B 分块 | -13.7% | -3.7% |
| 多种大小交替，1460 B 分块 | -6.4% | +3.8% |
| 极小 data，整块 / 1460 B 分块 / 每事件一块 | +2.9% / +2.5% / +2.4% | 约 +2%～3% |
| 极小 data，4 B 分块 | +1.0% | +0.7% |
| 普通单行 JSON，1460 B 分块 | +2.3% | +3.0% |
| metadata / 普通多行，1460 B 分块 | +7.8% / +2.6% | +0.2% / 接近 0 |
| CRLF JSON，1460 B 分块 | +5.3% | -0.7% |
| 心跳，整块 / 1460 B 分块 / 4 B 分块 | -0.2% / -2.7% / +2.4% | 约 0 / -0.3% / +1.9% |

两个主要收益成立：长文本校验的收益主要来自第一步，混合记录的容量与吞吐收益主要来自第二步。短记录没有获得普遍加速，并且部分场景有小幅额外开销。metadata 的变化在不同测量中也有波动，不将它全部归因于某条指令或某个分支。

额外尝试了仅对 data 使用 SIMD、把紧凑复制抽到 cold 函数两种实现；它们没有改善整体取舍，个别场景更慢，未采用。原始结果保存在 [候选比较](bench-rollout-2026-09-11/short-path-candidates-summary.csv)。

**Criterion 与编码复核**

使用相同负载又跑了一轮 Criterion：每实现 40 个样本、预热 150 ms、测量目标 700 ms，保留 mean/median 和 95% CI。对有疑问的 9 个短消息、metadata、心跳和变长场景，轮换顺序再测两轮，每实现 50 个样本、预热 200 ms、目标 1 s。完整结果和原始 JSON 随实验归档保存，不剔除不利样本。

Criterion 确认了长 UTF-8 约 75%～80% 的耗时下降。混合负载的收益幅度与交错 harness 不完全一致，不能拼接绝对耗时。个别测量存在明显高耗时样本，例如 CRLF 的首次 mean 比值约为 1.239，但同轮 median 比值约为 1.050；因此短场景还需结合轮换顺序后的复核和配对测量判断。

重点场景的三轮 Criterion 复核如下：每轮先用 mean 计算最终实现/基线，再取三轮比值中位数。范围是三轮点估计的最小/最大值，不是置信区间。

| 场景 | 三轮耗时变化中位数 | 三轮范围 |
| --- | ---: | ---: |
| 极小 data，整块 | +1.8% | +1.7%～+2.6% |
| 极小 data，1460 B 分块 | +2.6% | +1.8%～+13.8% |
| metadata，1460 B 分块 | +4.5% | +2.9%～+5.4% |
| 普通多行，1460 B 分块 | +3.6% | +3.6%～+3.6%（四舍五入） |
| 心跳，整块 | +5.7% | +1.3%～+11.0% |
| 心跳，4 B 分块 | +2.4% | +2.2%～+2.9% |
| CRLF JSON，1460 B 分块 | +4.9% | +4.1%～+23.9% |
| data 后接 metadata，1460 B 分块 | +2.1% | -2.1%～+2.9% |
| 多种大小交替，1460 B 分块 | -8.8% | -12.7%～-5.4% |

这些数据确认了短场景的小幅开销，不能把它们全部归为噪声；较大的偶发偏差也完整保留。

另用借用切片加 futures ready 输入复测了 8 个代表负载：最终实现的长 UTF-8 约 -78.6%，大小混合 JSON/多行约 -21.7%/-15.4%，4 B 小消息约 +1.0%，metadata 约 +2.1%，10 B 中等消息约 +1.3%。两种输入模式同时改变了所有权与 Pending 行为，只用于检查优化的适用范围，不能将差值全部归给某一个输入成本。[借用输入统计](bench-rollout-2026-09-11/borrowed-summary.csv)。

与 sse-core 比较，第一轮 Criterion 中长 UTF-8 的耗时约为其 20%～25%；极小 data 的整块与 1460 B 分块仍约慢 25%，4 B 分块约慢 8%。这两步没有解决此前定位的小事件处理流程成本，不能据此声称所有场景领先。

编码方面，Criterion 使用 iter_batched，把构造拥有所有权的 Sse 放在计时外，只测已有 Sse 到 Bytes 的转换。第一轮最终实现相对基线：小 JSON 约 -82%、带 metadata 的小 JSON 约 -36%、大 ASCII/UTF-8 约 -44%/-43%、空 data 加 retry 约 -49%。这些数值不包含 JSON 序列化；实际应用中的整条发送流程收益会更小。交错 harness 的 encode_owned 则包含字符串克隆，统计口径不同，单独保存。

**容量诊断**

一条约 40 KB 的两行 data，随后 1000 条 `data: x\ndata: y\n\n`，采用 1460 B 分块：

| 指标 | 基线 / 第一步 | 第二步 |
| --- | ---: | ---: |
| alloc 次数 | 1003 | 1003 |
| realloc 次数 | 5 | 5 |
| 分配与扩容申请字节累计 | 46,762,420 | 141,420 |
| 输出 data capacity 累计 | 46,670,624 | 49,624 |
| 最后一个 3 B data 的 capacity | 46,624 | 3 |

这是累计申请量和输出容量，不是进程 RSS。诊断消费者立即丢弃输出；另有回归测试保留所有输出，检查后续小消息不会携带大容量。解析器仍保留一个大累积缓冲区，以维持未来分片大消息的效率。

**验证与复跑**

已通过 all-features 下的 41 个解析/编码测试、2 个本机 HTTP 集成测试（Hyper、Reqwest 各 100000 条事件）和 3 个文档测试。无默认 feature 的 41 个测试，以及仅 memchr、仅 simdutf8 的 UTF-8 扩展测试均通过。额外比较了第一步、第二步与修正基线在各种切分、随机块布局、有效 Unicode、非法 UTF-8、重复字段及错误恢复输入上的输出等价性。Clippy 全目标全 feature 且拒绝警告、格式检查均通过。

测试中的 HTTP 监听曾被沙箱拒绝，随后使用已授权的沙箱外 cargo test 完成了本机集成验证。性能数据来自预构造的 Bytes 与内存输入流，不包括网络/TLS，也不代表实际请求延迟。尚未测 ARM 性能、长期并发连接的 p99/RSS，也未运行 Miri 或长期 fuzz。

仓库可用 `cargo bench --bench bench -- --quick` 快速运行；去掉 --quick 使用现有默认测量配置，或者用过滤词选择场景。前后版本、交错 runner、Criterion runner、负载、等价性测试和容量诊断均在 [实验归档](bench-rollout-2026-09-11/experiment.zip)。解压后的 study 目录可运行 `cargo test --release --test equivalence`、`STUDY_VARIANTS=baseline,step1,step2,core cargo run --release`、`cargo bench --bench compare`。Linux 性能复跑时应选定本机合适的 CPU；STUDY_VARIANTS、STUDY_CASES、STUDY_OUTPUT、STUDY_MODE=borrowed 可选择交错测量范围。
