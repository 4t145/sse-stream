2026-09-11：短消息完成路径与 data 扫描优化

已落地完整 data 行后紧接 LF 空行时直接完成事件，并调整 data 值与注释的处理顺序。相对本轮优化前的工作区，短 JSON 耗时下降约 **11–16%**，小消息 TCP 约 **11–13%**，多行 data 约 **16–17%**。这里的范围来自三轮 Criterion 与最终交错诊断两种测量方式，不是置信区间。比较基线已包含上一轮的 SIMD UTF-8、编码预分配和自适应容量改动，不能把本轮百分比理解为相对 crates.io 发布版。

本轮保留的改动：

- `data: ...\n\n` 在处理 data 行的同一轮直接 dispatch，保持原 UTF-8 校验和容量策略。前面已有 metadata 或其他 data 行时仍会完整保留，其他换行形式继续走通用处理。
- 提前识别并复用 `data:` 后的切片，扫描字段值时，短输入用标量、较长输入用 memchr2，避免重复检查固定前缀。generic 行扫描保持原策略。
- 完整注释先于 data 路径处理；跨块注释继续按 tracing 是否需要内容决定保存或丢弃，避免扫描调整拖慢心跳。

正式性能验证完整覆盖现有 **28 个解码 + 5 个编码场景**，三轮轮换 baseline/current/core，每项 40 samples、150 ms 预热、700 ms 目标测量时间、10,000 bootstrap resamples。另对五个有波动或作为对照的场景反向轮换补测两轮，每项 80 samples、200 ms 预热、2 s 目标测量时间。最终实现又经过 51 轮全场景交错诊断。所有计时都固定逻辑 CPU 2，串行运行；i5-13600K、Rust 1.98.0、默认 features、无额外 RUSTFLAGS / LTO，CPU 未锁频。

与 sse-core 的差距需要按测量方式区分。正式 Criterion 全量测试中，小消息 TCP、短单行 JSON 已进入约 ±3% 的接近区间；metadata、多行 data、混合消息和 Unicode 保持优势。不过，在额外的交错诊断中（rt.block_on 驱动，有不同的包装和编译上下文），结果为：

| 场景 | 当前比 core 多用时间，51 轮中位值 |
|---|---:|
| `small_data_whole_stream_chunk` | +4.0% |
| `small_data_tcp_chunks` | +3.5% |
| `json_line_tcp` | +25.4% |

这说明短消息的跨库排名仍对 harness / 构建上下文敏感，不能宣称已稳定追平或全面超越。两种测量都确认了相对自身基线的收益。仍明确落后的是 4 B 小消息和 4 B 心跳；本次这两项相对自身基线仅约 +1% 波动，没有解决每块 poll、状态恢复和输入对象的成本。按行到达的心跳也仍有少量差距。

选择当前实现的依据：直接将长切片交给 memchr2，会让短 CRLF 注释耗时增加约 150%；缩短所有行的标量前缀至 4/8 B，会让普通心跳退化约 25–43%，并影响 10 B 碎片。因此没有采用这些全局策略。对 data 值单独扫描后，再提前处理注释，才同时保住短块表现并获得短消息收益。各候选与单项数据保留在归档，不能把不同候选的改善百分比直接相加。
